# ご連絡：0.6.1 を公開しました（公開前の監査で6件を直しています）

同梱と実機確認、ありがとうございます。タグを打つ前に **`embed` / `search` の一式を
監査**したところ、**黙って間違う書き方が6件**見つかったので直してから 0.6.1 を出しました。

**本体側の対応は不要です。** 契約（`ai-embed` の受け渡し）は一切変えていません。

---

## なぜ監査したか

0.6.1 のコード差分そのものは9行でしたが、**学校で実際に動くのは 0.6.0 で入った
`embed` / `search` 一式**です。差分だけでなく、その一式を対象にしました。

探したのは「例外にならず、それらしい答えが返ってしまう」書き方です。教材では
これがいちばん困ります。先生も生徒も、間違っていることに気付けません。

## 見つかったもの（すべて修正済み）

### 1. 文字列を渡すと、1文字ずつ別の文になっていました

    ai.search("怖い本", "あいうえお")
    → 「あ」「い」「う」「え」「お」を5冊の本として検索していた

例外にならず、それらしい結果が返っていました。`ValueError` で止めます。

### 2. 辞書を渡すと、説明文が消えていました

    ai.search("怖い本", {"真夜中の校舎": "深夜の学校に…"})
    → 題名だけを検索対象にし、説明文を捨てていた

**蔵書検索でいちばん起きやすい書き間違い**です（本の一覧を辞書で持つのは自然なため）。
これも例外にならず、それらしい結果が返っていました。

### 3. 本体のベクトルを、1本目しか検算していませんでした

**これがいちばん重い見落としです。こちらの実装の穴でした。**

前回お伝えした「次元の検算」は、**1本目だけ**を見ていました。途中から長さの違う
ベクトルが混じった場合、素通りします。そのうえ内積が `zip` で短いほうに切りそろえる
ため、**近い順だけが静かに狂います**。

全部のベクトルを確かめ、内積も長さが違えば拒むようにしました。

### 4〜6. 原因が読み取れないエラー

| 書き方 | 前 | 後 |
| --- | --- | --- |
| `ai.embed(123)` | `'int' object is not iterable` | 「texts には文のリストを渡してください」 |
| 本体が壊れたベクトルを返す | `could not convert string to float: '文'` | 「本体が返したベクトルに、数でないものが混じっています」 |
| 件数に上限なし | 100万件なら 3907 往復してブラウザが落ちる | 10,000 件で理由を添えて止める |

## こちらの実装ミスも1件ありました

埋め込みモデルの二重読み込みを防ぐ鍵を入れたのですが、**生成用の鍵を使い回して
いました**。生成中に `embed()` を呼ぶと、生成が終わるまで待たされます。`embed()` は
イベントループの上から呼ばれるので、**ノートブックごと固まります**。

鍵を分けました。テストでは実際に生成中の状態を作り、読み込みが返ってくることを
確かめています（属性を比べるだけでは、この取り違えを捕まえられませんでした）。

## 調べて問題が無かったもの

| 観点 | 結果 |
| --- | --- |
| 本体の応答が画面（HTML）に出る経路 | **ありません**。`search()` が返す `text` は利用者が渡した文書そのもので、本体由来ではありません |
| `_call_host` を包んだこと（0.6.0）の影響 | `ai-probe` は失敗しても従来どおり続き、`ai-load` の失敗は読める例外になります |
| 送っている内容 | `{"model", "texts"}` のみ。それ以外は送っていません |
| エラー文言からの情報漏れ | ありません |
