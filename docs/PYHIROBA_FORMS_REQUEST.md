# ご相談：PyHiroba でフォーム入力を Python に返せるようにしていただきたい

library-hiroba の開発者です。いつもお世話になっております。

**お願いしたいこと**：PyHiroba 本体に、画面のフォームで入力された値を Python 側へ渡す経路を1つ足していただけないでしょうか。変更は `js/app.exec.js` と `js/pyodide-worker.js` の2ファイル、合計 40 行ほどの見込みです。設計・検証・library-hiroba 側の実装はすべて済んでおり、**本体側で決めていただく点も4つに絞ってあります**。

技術的な詳細は [`PYHIROBA_FORMS.md`](PYHIROBA_FORMS.md) にまとめました。この文書はその要約と、なぜ今お願いしているかです。

## なぜ必要か

いま PyHiroba では、`ui.form()` は**表示されるがボタンを押しても何も起きません**。そのため、次の教材が PyHiroba では作れず、Google Colab 専用になってしまいます。

- **AI とのチャット** — 生徒が質問を打ち、AI が答える形式
- 入力を受け取って処理する演習全般（計算、判定、アンケート、答え合わせ）

library-hiroba の中心にあるのは「同じコードが Colab でも PyHiroba でも動く」ことです。表示部品（`ui`）と文章生成（`ai`）はどちらでも動いており、**足りないのは画面の入力を Python に渡す道だけ**です。ここが埋まると、上の教材がそのまま両方で動くようになります。

生徒が AI と対話する教材は需要が大きく、ここが空いているのがいちばん惜しい状態です。

## なぜ今の作りでは動かないのか（実測に基づく事実）

| 調べたこと | 結果 |
|---|---|
| `js/pyodide-worker.js` の stdin | 実装がありません。`input()` は使えません |
| セルの実行方式 | セル全体を同期実行し、終わってから出力を返します。途中で止めて入力を待つ経路がありません |
| 出力 → ワーカーの通信路 | ありません（`app.exec.js` は結果を一方向に描画します） |

出力の中にどのような HTML を置いても、値が Python に戻る道がありません。**これは library-hiroba 側の工夫では埋められない部分**です。

なお、ワーカーを止めて入力を待つ `Atomics.wait` / `SharedArrayBuffer` は使えません。`COOP` / `COEP` ヘッダーが必要で、GitHub Pages では付けられないためです（`js/theme.js` にも同じ理由の記述があります）。この方式は最初から選択肢から外してあります。

## 提案する方式：コールバック

セルの実行を止めません。フォームを表示していったんセルを終え、**押されたときに登録済みの Python 関数を呼び直す**形です。いまの同期実行の作りを変えずに済みます。

```
[セル実行]  Python: フォームを表示し、関数を登録
             ↓ 出力（HTML）
[画面]      利用者が入力してボタンを押す
             ↓ postMessage（本体の JS が送る）
[ワーカー]   登録された関数を値付きで呼ぶ
             ↓ 戻り値の _repr_html_()
[画面]      フォームの下の出力欄を差し替える
```

## お願いする変更（2ファイル）

**1. メインスレッド側（`js/app.exec.js`）** — 出力を挿入した直後に、`data-hui-submit` を持つボタンへクリックを登録し、`data-hui-field` の値を集めて `postMessage` する。

**2. ワーカー側（`js/pyodide-worker.js`）** — フォーム ID から Python 側のフォームを引いて呼ぶ。引く口は library-hiroba が用意します（`library_hiroba.ui.get_form(form_id)`、見つからなければ `None`）。

いずれも、そのまま貼れる形のコードを [`PYHIROBA_FORMS.md` の第6節](PYHIROBA_FORMS.md) に書いてあります。

**値の型は気にしていただかなくて大丈夫です。** `el.value`（常に文字列）をそのまま送ってください。数値欄との差は library-hiroba の `submit()` が吸収します。

## 安全性について

**サニタイザの設定を緩める必要はありません。** DOMPurify 3.4.12 に PyHiroba の `sanitizeHtml()` と同じ設定で通して確認済みです。

| 要素・属性 | 結果 |
|---|---|
| `data-hui-*` 属性 | そのまま残ります |
| `<input>` `<textarea>` `<select>` `<option>` `<button type="button">` | 残ります |
| `<form>` | 除去されます（今回は使いません） |

設計上も、次のようにしてあります。

| ご懸念 | この設計での扱い |
|---|---|
| 出力の HTML が勝手に動くのでは | 動きません。イベントを登録するのは**本体の信頼できるコード**で、出力側は `data-*` の目印を持つだけです |
| 教材が任意の JavaScript を実行できるのでは | できません。`<script>` もイベント属性も禁止のままです |
| 値の受け渡しでコードが実行されるのでは | されません。渡るのは `postMessage` の文字列だけで、呼び出し先は Python 側が自分で登録した関数に限られます |
| 別の教材のフォームを乗っ取れるのでは | できません。ID は実行のたびに一意です |
| 登録が無限に増えて重くならないか | library-hiroba 側で最大 64 件に制限しています |

また、画面から送られた値のうち **`fields` に宣言された欄だけ**を受け取り、それ以外は捨てます。検証ツールで画面を書き換えられても、`handler` が受け取る引数は教材に書かれた Python のほうが正となります。

## 決めていただきたいこと（4点）

1. 引く口を `library_hiroba.ui.get_form(form_id)` にするか、本体側で好みの名前（`__hui_forms__` のような辞書）に合わせるか
2. 結果の差し替え先を `data-hui-output` にするか、セルの出力全体を描き直すか
3. フォームの登録をいつ捨てるか（セル削除時、再実行時、ノートブックを閉じたとき）
4. `await` と非同期の反復子を処理する場所を、本体のどこに置くか

**これらが決まれば、library-hiroba 側は登録の口を合わせるだけで対応できます。** ご都合のよい形に合わせますので、決めやすいほうをお知らせください。

## いま PyHiroba で開いた場合の見え方

対応が入るまでのあいだ、`ui.form()` を PyHiroba で開いた教材には、**押しても何も起きない入力欄だけが出る**状態になります。書いた先生がご自分の誤りを疑ってしまうため、library-hiroba 0.5.0 では、PyHiroba 上では注意書きを添えて表示するようにしました。対応が入り次第、この注意書きは外します。

## 補足：AI の逐次出力（対応は任意です）

`ai.stream()` は答えを書けたところから受け取る機能ですが、**本体の対応は任意**です。`ai-ask-start` / `ai-ask-next` を本体が知らない場合は既存の `ai-ask` に自動で切り替わり、全文が一度に返ります。まずはフォームだけで十分です。
