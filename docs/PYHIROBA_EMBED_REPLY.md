library-hiroba の開発者です。ご依頼ありがとうございます。

**結論：お引き受けします。** ご提案の橋（`ai-embed`）と目印（`pyhirobaFeatures`）は、

## 1. 実在・サイズ確認は、こちらで済ませました

「本体の『使えるモデルを調べる』で確認してから確定」とありましたが、
こちらから huggingface.co に到達できたため、先に確認しました。**ご提案の候補は
4つとも実在し、見積り（110–120MB・384次元）も正確でした。**

| リポジトリ | 実在 | int8 サイズ | 次元 | プーリング |
| --- | --- | --- | --- | --- |
| `Xenova/paraphrase-multilingual-MiniLM-L12-v2` | ✓ | 118.3MB | 384 | mean |
| `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | ✓ | — | 384 | mean |
| `Xenova/multilingual-e5-small` | ✓ | 118.3MB | 384 | mean |
| `intfloat/multilingual-e5-small` | ✓ | — | 384 | mean |

- **両経路とも mean pooling** です。本体が約束される「mean pooling + normalize」と
  一致するので、ベクトルの意味が環境でずれる心配はありません。
- `onnx-community/multilingual-e5-small` は**存在しません**（401）。ONNX 側は
  `Xenova/...` をご指定ください。

## 2. 【お願い1】q4 ではなく int8 を選んでください

**同じモデルで、4bit のほうが 3.4 倍大きくなります。** 実測です。

| ファイル | 大きさ |
| --- | --- |
| `model_quantized.onnx`（int8） | **118MB** |
| `model_q4.onnx` | **399MB** |

理由は Qwen3 0.6B のときと同じで、`onnx-community` / `Xenova` の q4 は
**MatMul の重みだけを 4bit にし、埋め込み（`Gather` 演算）は fp32 のまま残す**ためです。
このモデルは語彙が 250037 と大きく、埋め込みだけで 96M パラメータ
（fp32 で 384MB）を占めます。計算でも再現しました。

| | 推定 | 実測 |
| --- | --- | --- |
| int8（全体 1byte） | 117MB | 118MB |
| q4（埋め込みだけ fp32） | 396MB | 399MB |
| （もし埋め込みも 4bit なら） | 59MB | — |

**「4bit だから軽い」で選ぶと、校内の回線に 399MB が流れます。** ご確認ください。

## 3. 【お願い2】既定は MiniLM を推奨します（E5 は接頭辞が API と噛み合いません）

ご依頼では「E5 の接頭辞は library 側で内部的に付けて、生徒には意識させない」と
ありましたが、**これは `embed()` の形では原理的にできません。**

E5 のモデルカードは、こう明記しています。

> Each input text should start with "query: " or "passage: ", even for non-English texts.

ところが `ai.embed(texts)` は**対称な API で、渡された文が query なのか passage なのかを
知りません**。`search(query, documents)` は区別できますが、ご提示の教材イメージ後半にある
「`embed` だけで書く例」は、E5 を既定にすると正しく動きません
（両方に同じ接頭辞が付くか、どちらにも付かないため）。

**MiniLM なら接頭辞が不要で、`embed()` 単体でも `search()` でも意味が一貫します。**
サイズ・次元・プーリングは E5 と同一（118MB / 384 / mean）なので、失うものもありません。

E5 も併載する場合は `embed(texts, kind="query"|"passage")` のような指定が必要になり、
「生徒に意識させない」という当初の狙いとは逆になります。**第一候補どおり MiniLM を
既定にする**のが素直だと考えます。

## 4. 【お願い3】モデルキーを合わせてください

本体の `js/ai.js` と食い違うと「許可されていません」で落ちるとのことなので、
先にご提案します。既存のチャット側の命名（`qwen05` / `llmjp150m`）に倣いました。

| キー | 本体が読む ONNX | Colab で使う id |
| --- | --- | --- |
| `minilm`（既定） | `Xenova/paraphrase-multilingual-MiniLM-L12-v2` | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` |
| `e5small`（任意） | `Xenova/multilingual-e5-small` | `intfloat/multilingual-e5-small` |

この名前でよろしければ、そのまま実装します。変えたい場合はご指定ください。

なお **`ai.load()` に埋め込みモデルのキーは通しません**。library 側で
チャット用とは別の一覧として持つためです（理由は次節）。

## 5. library 側で吸収すること（本体側の対応は不要です）

ご参考まで、こちらで引き受ける設計判断です。**本体に影響するものはありません。**

- **埋め込みモデルは、チャットの `MODELS` とは別の一覧にします。**
  同じ辞書に入れると `ai.models()` の一覧に混ざり、`ai.load("minilm")` が成功して
  非生成モデルがチャット側に載り、`ai.recommend()` が埋め込みモデルを「おすすめ」に
  選びうる、という3つの壊れ方をするためです。
- **Colab 側は `sentence-transformers` を使いません。** あれは
  `transformers>=5.0.0` を要求し、Colab の既存 transformers と衝突しうるうえ、
  scikit-learn と scipy を引き連れます。mean pooling + L2 正規化は
  `transformers` + `torch`（既存の依存）だけで書けるので、追加の依存は増やしません。
  **本体と同じ処理を自前で書くぶん、両経路の一致も保証しやすくなります。**
- **`search()` は numpy を必須にしません。** 10冊×384次元なら純 Python の内積で
  十分です（教材例で利用者が numpy を使うのは自由です）。
- 返ってきたベクトルが L2 正規化されているかを、安価に一度だけ検算します。
  本体側の不具合に気付ける保険としてです。

## 6. こまごました確認

  問題になりませんが、先に決めておければ）。

  了解しました。目印が無い本体では、日本語で理由の分かるエラーにします。

## 7. 補足：チャット側の未公開の修正について

別件ですが、**`ai.talk().form()` が「考え中」のまま止まる不具合**の修正が、
まだ PyPI に出ていません（`main` にはあります／0.5.4）。原因は
`TextIteratorStreamer` を timeout 無しで作っていたことで、生成が黙ると
読み出しが永久にブロックしていました。埋め込みの追加は 0.6.0 になりますが、
**先に 0.5.4 を出しておくほうが安全**だと考えています。
